# PC .227: hardware watchdog plan

Status: plan only, 2026-10-26. **Nothing in this document has been applied.**
Every step in "Steps" changes `.227` and needs Ted's typed approval before it
runs (charter: changing anything on `.227` is an explicit-approval action).
Follows `handoffs/session-handoff-2026-10-26-227-freeze.md` recommendation 1.

Scope: `.227` host only (`lcdash-server`, `14.1.1.227`) and the three
`mindshare-radio-*` services. Hermes (Ollama, ComfyUI, n8n) is out of scope
except for the risk note below.

## Goal

A future hard freeze like 2026-10-25 07:21 EDT (28.5 hours down, no logging,
no shutdown entry) should reset the host within about a minute, after which
the three enabled radio services start on their own.

Not verified (cannot be read without changing something or without root):

- Whether the BIOS leaves the TCO "no reboot" strap off. If it is set, the
  driver loads but refuses to arm ("reboot disabled by hardware/BIOS" in
  `dmesg`). Step 1 reveals this; see "If the driver will not arm".
- That `modprobe iTCO_wdt` by name overrides the Ubuntu blacklist. This is
  standard kmod behaviour (a blacklist only stops alias autoloading, and
  `systemd-modules-load` loads by name), but it is proven only by Step 1.
- The cause of the freeze. A watchdog restores service; it does not explain it.

## Design

1. Load `iTCO_wdt` by explicit name, now (Step 1) and at every boot through
   `/etc/modules-load.d/` (Step 2). Do not edit the Ubuntu-generated
   blacklist: it is rewritten per kernel package and would reappear.
2. Have systemd (PID 1) arm and pet the device: `RuntimeWatchdogSec=60`.
   PID 1 pets it from its event loop, so a hang that stops PID 1 or the whole
   kernel stops the petting and the chipset resets the board after 60 s.
3. `RebootWatchdogSec=5min` so a shutdown or reboot that wedges is also reset
   (the default is 10 min, which is close to the TCO maximum of about 614 s).
4. The reset is a hard power-cycle-style reboot, like Ted's manual one:
   ext4/LVM journal replay at boot, nothing flushed. The radio uploader
   already tolerates restarts (queue and parked directories persist).

## Steps

Each step is a separate approval. Ted types the approval line shown, then the
step runs, then its check is read before the next step is requested. Run all
commands as `administrator` over SSH
(`ssh -o IdentitiesOnly=yes -i ~/.ssh/lcdash_server_ed25519 administrator@14.1.1.227`).
Pick a quiet time; the planned reboots below cost the radio listener about two
to three minutes of capture each.

### Step 0: read-only pre-check (no approval needed)

```bash
systemctl show -p RuntimeWatchdogUSec -p RebootWatchdogUSec
ls /sys/class/watchdog /dev/watchdog* 2>&1
systemctl is-active mindshare-radio-capture mindshare-radio-transcribe mindshare-radio-upload
```

Expect `RuntimeWatchdogUSec=0`, no watchdog device, three `active`.

### Step 1: load the module now

Approval line: `APPROVE WDOG-1 load iTCO_wdt on .227`

```bash
sudo modprobe iTCO_wdt
```

Check:

```bash
lsmod | grep -E "iTCO"
ls -l /dev/watchdog /dev/watchdog0
cat /sys/class/watchdog/watchdog0/identity /sys/class/watchdog/watchdog0/timeout /sys/class/watchdog/watchdog0/nowayout
sudo dmesg | grep -i -E "iTCO|tco|watchdog" | tail
```

Expected: `iTCO_wdt` and `iTCO_vendor_support` in `lsmod`, `/dev/watchdog0`
present, identity `iTCO_wdt`, a `dmesg` line like `Found a Intel PCH TCO
device (Version=6, ...)` (version number may differ) and `initialized`.
`nowayout` must be `0` (otherwise rollback needs a reboot). Loading does not
reboot anything by itself and systemd does not use the device until Step 3.
Stop here and report if `dmesg` says the reboot is disabled by hardware/BIOS.

### Step 2: load the module at every boot

Approval line: `APPROVE WDOG-2 persist iTCO_wdt on .227`

```bash
echo iTCO_wdt | sudo tee /etc/modules-load.d/watchdog.conf
cat /etc/modules-load.d/watchdog.conf
```

Check: the file contains exactly `iTCO_wdt`. It is proven at boot in Step 5.

### Step 3: arm systemd's watchdog (backup first)

Approval line: `APPROVE WDOG-3 edit system.conf and daemon-reexec on .227`

```bash
sudo cp -a /etc/systemd/system.conf /etc/systemd/system.conf.bak-20261026
sudo sed -i -e 's/^#RuntimeWatchdogSec=off$/RuntimeWatchdogSec=60/' \
            -e 's/^#RebootWatchdogSec=10min$/RebootWatchdogSec=5min/' \
            /etc/systemd/system.conf
diff /etc/systemd/system.conf.bak-20261026 /etc/systemd/system.conf
```

The `diff` must show exactly the two changed lines and nothing else
(`RuntimeWatchdogSec=60`, `RebootWatchdogSec=5min`); if it shows anything
else, stop and restore the backup (Rollback, step R1). Then:

```bash
sudo systemctl daemon-reexec
```

`daemon-reexec` re-reads `system.conf` without a reboot and keeps services
running. Step 1 must already have succeeded: with no `/dev/watchdog0` systemd
only logs a warning and stays unarmed.

### Step 4: verify it is armed (read-only)

No separate approval beyond Step 3 (all reads):

```bash
systemctl show -p RuntimeWatchdogUSec -p RebootWatchdogUSec -p WatchdogDevice
journalctl -b _PID=1 --grep -i watchdog --no-pager | tail
cat /sys/class/watchdog/watchdog0/state /sys/class/watchdog/watchdog0/timeout
sudo fuser -v /dev/watchdog0
systemctl is-active mindshare-radio-capture mindshare-radio-transcribe mindshare-radio-upload
```

Expected: `RuntimeWatchdogUSec=1min`, `RebootWatchdogUSec=5min`, a PID 1 log line
about setting the watchdog timeout, `state` `active`, `timeout` `60`, and
`fuser` showing PID 1 (`systemd`) holding the device. The three radio units
stay `active` and the pilot's `radio-heartbeat` keeps arriving. (The
`/sys/class/watchdog` file names are the kernel's standard ones, not yet
confirmed on this host; if one is missing, the `systemctl show` and `fuser`
lines are the authoritative checks.)

### Step 5: planned-reboot proof (boot-time load and service recovery)

Approval line: `APPROVE WDOG-5 planned reboot of .227`

```bash
sudo systemctl reboot
```

After it is back (about 2 minutes), repeat the Step 4 checks without doing
anything else. Required result: `/dev/watchdog0` exists with no manual
`modprobe`, systemd reports 1min armed, the three radio units are `active`
with no operator action, and the AWS pilot shows `radio-heartbeat ok` again
(the `lcdash-p1-logan-use1-radio-listener-silent` alarm may flip to `ALARM`
for the gap and clears after two clean 5-minute periods).

### Step 6: simulated freeze proof (the watchdog actually resets the box)

Approval line: `APPROVE WDOG-6 simulate kernel hang on .227`

Only after Step 5 passed. This deliberately crashes the kernel, so Ted must be
available (and, if possible, near the machine) in case it does not come back.

```bash
sudo sync
echo 1 | sudo tee /proc/sys/kernel/sysrq
echo c | sudo tee /proc/sysrq-trigger
```

`sysrq-trigger c` panics the kernel. Because `kernel.panic = 0` the kernel
does not reboot itself; PID 1 is no longer petting the device, so the TCO
timer should reset the board about 60 s later. Expected: SSH drops, the host
answers again within about 2 to 3 minutes, `journalctl --list-boots` shows a
new boot whose predecessor has no clean shutdown entry, the radio units are
`active`, the uploader heartbeat resumes. If the host has not returned after
5 minutes, Ted power-cycles it by hand and the result is reported as a
failure; do not retry blindly.

## Rollback

Approval line for each use: `APPROVE WDOG-R rollback watchdog on .227`

```bash
# R1: restore systemd config and disarm
sudo cp -a /etc/systemd/system.conf.bak-20261026 /etc/systemd/system.conf
sudo systemctl daemon-reexec
systemctl show -p RuntimeWatchdogUSec          # expect 0
# R2: stop loading it at boot
sudo rm /etc/modules-load.d/watchdog.conf
# R3: unload (only after R1 shows 0; nowayout is 0, so this is allowed)
sudo rmmod iTCO_wdt
ls /dev/watchdog* 2>&1                          # expect: no such file
```

R1 alone is the safe disarm: with `RuntimeWatchdogSec` back to off, systemd
closes the device cleanly and the timer stops. If the box is already stuck in
a reset loop, power it off, boot, and run R1 and R2 quickly (the loop would
need the module loaded and the config armed, so removing either breaks it).
The backup `system.conf.bak-20261026` is kept until Ted says to delete it.

## If the driver will not arm

If Step 1 reports the TCO reboot as disabled by hardware or BIOS, or
`/dev/watchdog0` never appears, stop; nothing from Steps 2 and 3 should run.
Options for Ted to choose (a BIOS visit is a new approval): look for a
watchdog or "TCO / ME" setting in the ASUS BIOS (1402), or fit an external
watchdog or smart plug. `softdog` is **not** an alternative: it is a software
timer driven by the same kernel that froze, so it cannot recover a hard
freeze.

## Known risk: a long GPU job can be rebooted if userspace hangs

The watchdog cannot tell "frozen" from "busy". The reset fires if PID 1 fails
to pet the timer for 60 s. That normally takes a real hang, but it can also be
caused by:

- a GPU or driver fault that stalls the whole kernel or all CPUs for a minute
  (the same class of event the watchdog is meant to catch);
- extreme memory or I/O pressure from a Hermes job (125 GiB RAM and a 16%-full
  disk make this unlikely) that starves PID 1;
- a persistent fault that recurs after every boot, causing a reboot loop
  (Rollback R1 and R2 break it).

A watchdog reset is a hard reset: any in-flight Ollama, ComfyUI or n8n job is
lost and its state is only as good as the filesystem journal. This plan does
not change how the Hermes containers restart after a reboot; whether they come
back is unverified and out of scope. The radio services come back by
themselves (enabled, `multi-user.target`). The trade accepted here is a rare
unclean reset in exchange for never again losing about 28 hours of radio audio
to a silent freeze.
